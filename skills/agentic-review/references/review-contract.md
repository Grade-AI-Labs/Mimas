# Review Contract (agentic-review)

Use this contract for all specialist subagents and for final consolidation.

Audit mode defaults:
- `completion_mode: fail-closed`
- transparency mode: `summary + artifact links`
- signature model: structured attestation metadata (not cryptographic signatures)

## Severity Scale

- `critical`: likely production outage, data corruption/loss, serious security exposure, or irreversible failure
- `high`: major functional breakage, integrity risk, or high-probability regression with broad impact
- `medium`: meaningful defect/risk with limited blast radius or clear workaround
- `low`: minor defect, low-risk maintainability issue, or quality gap with limited near-term impact

Use only these four values.

## Required Finding Schema

Every finding must include:

```yaml
severity: critical|high|medium|low
title: short defect summary
evidence:
  file: path/to/file
  line: 123
impact: why this matters in runtime/business terms
recommended_fix: concrete corrective action
confidence: high|medium|low
```

Additional optional fields are allowed (`owner`, `notes`, `related_findings`) but never omit required fields.

Recommended optional field when relevant:

```yaml
standards_policy_refs:
  - ENGINEERING.md#<section>
  - RP-<MODULE>-00X
```

For deterministic policy-check violations generated by the orchestrator, `standards_policy_refs` should include the failing policy rule id (for example `RP-BILLING-006`).

## Specialist Prompt Skeleton

Use this as the base specialist prompt, substituting values:

```text
You are a specialist code reviewer for <specialist-name>.

Read these inputs first:
1. AGENTS.md
2. <docs-dir>/ENGINEERING.md
3. Relevant CONTEXT.md file(s)
4. <docs-dir>/review/<plan-file>
5. Scoped diff artifact: <diff-file>
6. This review contract
7. Policy files from <docs-dir>/review/policies/ (global + module) when present

Review goal:
- Find actionable defects and risks in your domain.
- Exclude style-only commentary unless explicitly requested by user.

Required output:
- If findings exist: return a list where each finding follows the required schema exactly.
- If none: return "no actionable findings" and include testing/verification gaps.
- Include `standards_policy_refs` when applicable (rule ids or sections from ENGINEERING.md/policy files).
- Include an attestation block:
  ```yaml
  attestation:
    status: findings-submitted|no-actionable-findings
    attestation_text: I reviewed the assigned scope and reported all actionable findings I could verify from the provided artifacts.
  ```

Focus:
- correctness, regressions, safety, and compatibility risks
- evidence-backed findings only
- practical recommended fixes
```

## Cross-cut Specialist Focus

- `tests-regressions`: missing test coverage for changed behavior, flaky/assertion gaps, broken test intent
- `migrations-data-safety`: destructive migrations, incompatible schema evolution, backfill/rollback hazards
- `security-authz`: authn/authz bypass risk, secret leakage, unsafe trust boundaries, broken permission checks
- `api-contract`: backward compatibility breaks, response/request shape drift, versioning/consumer risk

## Automated Policy Checks (Orchestrator-Owned)

The orchestrator may emit findings from machine-usable policy metadata before specialist dispatch.

Required v1 support:
- `automation.check_type: inheritance_suffix`

Evaluation expectations:
- run checks on the configured scope (default `changed-files`)
- parse nested automation metadata robustly (including indented YAML keys)
- for malformed automation metadata (for example missing selector/expectation fields), mark rule status `unknown` with explicit reason and continue
- emit normal findings for `fail` results using the required schema
- include rule-id references in `standards_policy_refs`
- report `unknown` when parsing/analysis is inconclusive and include verification guidance in testing gaps

## Deduplication Rules

When multiple specialists report the same root cause:
1. Keep one canonical finding.
2. Preserve the highest severity level reported for that root cause.
3. Use the clearest evidence (file/line and concrete impact).
4. Merge fix guidance if complementary; otherwise keep the most actionable fix.
5. Optionally annotate corroboration ("also flagged by api-contract/security-authz").

## Specialist Attestation Schema (Required)

The orchestrator must emit one attestation entry per dispatched specialist:

```yaml
specialist_slug: backend-api
specialist_type: module|cross-cut
assigned_scope: "backend/orders/** (5 files)"
status: findings-submitted|no-actionable-findings|failed|skipped|missing
signed_at: 2026-05-20T09:12:45Z
attestation_text: I reviewed the assigned scope and reported all actionable findings I could verify from the provided artifacts.
output_artifact_path: <docs-dir>/review/review-result-<...>.specialists/backend-api.md
```

Notes:
- `status` must be one of the listed values.
- `signed_at` is recorded by the orchestrator at specialist result capture time.
- When specialist output is absent, emit `status: missing` and document reason in report blockers.

## Completion-State Rules (Fail-Closed)

Compute `completion_state` from required specialist attestations:
- `complete`: all required specialists have `status` in `{findings-submitted, no-actionable-findings}`
- `incomplete`: any required specialist has `status` in `{failed, skipped, missing}`

When `completion_state` is `incomplete`, emit explicit blocker list entries that identify each failing/missing specialist and reason.

## Manifest Contract (Machine-Audit Output)

The orchestrator must write `review-manifest-<YYYYMMDD>-<HHMMSS>-<scope>.json` with at least:

```json
{
  "run_id": "20260520-091245-feature-orders",
  "target": {
    "mode": "pr|local",
    "base_ref": "origin/main",
    "head_ref": "HEAD",
    "branch": "feature/orders",
    "timestamp": "2026-05-20T09:12:45Z"
  },
  "changed_files": [],
  "specialist_roster": [],
  "routing_map": [],
  "attestations": [],
  "compliance_results": {},
  "completion_state": "complete|incomplete",
  "completion_blockers": []
}
```

## Final Output Contract

The orchestrator's final review output must include:

1. `Run metadata` (mode, refs, branch, timestamp, run id)
2. `Changed file inventory`
3. `Specialist routing matrix`
4. `Specialist attestation ledger`
5. `Findings` (deduplicated, severity-ordered)
6. `Standards compliance (ENGINEERING.md)` (explicit passes/violations with references)
7. `Project policy compliance`:
   - when policy files exist: include rule id, status (`pass|fail|unknown`), evidence references, and exception usage
   - when policy files are missing: include recommendation to run `review-policy-builder`
   - include audit-governance source (`policy-contract` or `fallback-defaults`)
8. `Testing gaps / unverified areas`
9. `Coverage + completion status` (`completion_state`, route completeness, attestation completeness, blockers when incomplete)
10. `Artifacts`:
   - canonical plan path (`<docs-dir>/review/review-plan-*.md`)
   - diff directory path (`<docs-dir>/review/review-plan-*.diffs/`)
   - specialist raw-output directory (`<docs-dir>/review/review-result-*.specialists/`)
   - result path (`<docs-dir>/review/review-result-*.md`)
   - manifest path (`<docs-dir>/review/review-manifest-*.json`)

If there are no actionable issues, explicitly state "no actionable findings" and still provide sections 6-10.
